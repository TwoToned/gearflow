# GearFlow Discord Bot — Claude Code Prompt

I'm building a Discord bot for **GearFlow** — a SaaS platform for AV/theatre production companies to manage assets, projects, and crew. GearFlow is built with Next.js 15, TypeScript, Prisma/PostgreSQL, and Better Auth. The bot should be a first-class integration, not a bolt-on.

**Core concept:** Every GearFlow project gets a corresponding Discord channel. Crew added to a project get added to that channel. The bot is the bridge between Discord and GearFlow.

---

## Phase 1 — Project & Channel Sync

When a project is created in GearFlow, the bot should automatically create a Discord channel in a designated category with the format `PROJECTCODE-projectname` (e.g. `TTP001-pippin`). The channel should be private — only assigned crew can see it.

When a user is added to a project in GearFlow (as PM or crew), they should be given access to the corresponding Discord channel — if their Discord account is linked (see enrollment below). When they're removed from a project, access should be revoked.

This means GearFlow needs to emit events (webhooks or a queue) when projects are created/archived and when crew assignments change. The bot should listen for and act on these.

---

## Phase 2 — Account Enrollment

Not all crew have GearFlow app access, but all crew have an email address stored against their GearFlow profile. The `/link` command uses email as the anchor.

**Flow:**

1. User runs `/link [email]` in Discord
2. Bot calls the GearFlow internal API to check if that email exists in the system — if not, responds ephemerally with an error
3. If found, GearFlow generates a short-lived signed token (e.g. JWT, 15 min expiry) and sends a magic link to that email
4. The magic link points to a GearFlow endpoint (e.g. `/discord/verify?token=...`) — this page doesn't require the user to be logged in, it just validates the token and writes the Discord user ID to their profile
5. Bot polls or uses a webhook callback to confirm linkage, then responds ephemerally to confirm success and grants channel access based on their current project assignments

There should also be an admin command `/unlink @user` for GearFlow admins.

**Important considerations:**
- The magic link endpoint should be unauthenticated — crew without GearFlow app access still need to complete it via email
- Store a `discordUserId` field on the GearFlow User/contact model — this applies to all people records, not just users with app login access
- Tokens should be single-use and expire after 15 minutes
- If a Discord user tries to `/link` again when already linked, respond ephemerally telling them they're already connected and who they're linked to

## Slash Commands & Modal Forms

The bot should make heavy use of Discord's native slash commands and modal forms (not just text responses) to create a polished UX. Design a clean command registration pattern from the start since this will grow.

**Commands to implement:**

- `/link [email]` — starts the GearFlow account enrollment flow as described above

- `/project info` — shows a summary card (embed) for the current channel's linked project: status, PM, crew count, dates

- `/project crew` — lists crew assigned to the project with their roles

- `/project doc [type]` — generates a project document and either posts it in the channel or DMs it to the requesting user. On run, presents a select menu to choose delivery method (post in channel / send to my DMs). The `[type]` argument should be a Discord string select so users pick from a list rather than typing freeform. Two example document types to implement as a pattern:
  - **Pick list** — all assets assigned to the project, grouped by category, with quantity and asset codes
  - **Call sheet** — crew list with roles, call times (if set on the project), and venue/location details

  Use these two as the reference implementation. GearFlow already has a PDF generation system built in — check the existing codebase for the PDF generation utilities and use the same approach for all documents generated by the bot. Keep the document types as a clean registry so additional types can be added easily down the road. PDFs are sent as file attachments in Discord.

- `/incident report` — opens a Discord modal form with fields: title, description, severity (select menu), location. On submit, creates an incident record in GearFlow via the internal API and posts a formatted embed back to the channel confirming it

- `/asset lookup [code]` — looks up an asset by code in GearFlow and returns an embed with its details, test & tag status, and current assignment

- `/asset fault [code]` — opens a modal with fields: fault description, severity (select menu: minor / major / out of service), and an optional photo attachment. On submit, creates a fault record against the asset in GearFlow, updates the asset status accordingly (e.g. out of service flags it unavailable), and posts a formatted embed in the project channel confirming the fault has been logged with asset details and fault summary. If the asset is marked out of service, also post an alert into the configured `#asset-alerts` channel so management sees it regardless of which project channel it came from

- `/asset checkin [code]` — marks the asset as returned by the requesting Discord user, matched to their linked GearFlow profile. If the user isn't linked, respond ephemerally prompting them to run `/link` first

- `/asset checkout [code]` — marks the asset as checked out to the requesting Discord user, matched to their linked GearFlow profile. If the user isn't linked, respond ephemerally prompting them to run `/link` first

- `/unlink @user` — admin only, unlinks a Discord account from a GearFlow profile

- `/reconcile` — admin only, re-syncs all channel permissions against current GearFlow project assignments (useful after bot downtime)

Use Discord's interaction response types properly — modals for multi-field input, ephemeral responses where the output is only relevant to the person who ran the command, and rich embeds for any data being surfaced to the channel.

Structure commands as individual files under a `/commands` directory with a consistent interface so new commands are easy to add. Use a command handler that auto-registers them on startup.

## Role-Based Command Gating

Commands should be gated based on the user's GearFlow role on the project, synced at interaction time (not cached). Rules:

| Role | Commands |
|------|----------|
| Any linked crew member | `/link`, `/project info`, `/project crew`, `/asset fault`, `/asset checkin`, `/asset checkout`, `/incident report` |
| Project Manager or above | `/project doc`, `/project status` |
| GearFlow Admin | `/reconcile`, `/unlink`, `/asset lookup` across any project |

- If a user runs a command they don't have access to, respond ephemerally with a clear "you don't have permission" message that tells them what role is required
- Role is checked live against GearFlow via the internal API on each interaction — don't cache roles on the bot side

## Audit Log

- Maintain a private `#gearflow-log` channel in the Discord server that receives a feed of all bot actions across all projects — channel creation, crew access changes, document generation, incidents, asset faults, checkins/checkouts, and enrollment events
- Each log entry should be a clean embed with: action type, who triggered it, which project it relates to, and a timestamp
- This channel should be restricted to admins only (set via channel permission overwrites on bot startup)
- No commands needed for this — it's purely an automated feed

## Management UI — GearFlow Admin Panel

Add a **Discord Integration** settings page in the GearFlow admin panel (alongside existing settings). This is where admins configure and manage the bot without touching environment variables or Discord directly. Config options to expose:

- **Guild connection status** — shows whether the bot is connected to the Discord server, with a reconnect button
- **Channel category mapping** — which Discord category new project channels get created under (dropdown populated from the bot fetching available categories)
- **Alert channels** — configure which channels receive asset alerts, incident alerts, and the audit log (dropdowns populated from available channels)
- **Role mapping** — map GearFlow roles (Admin, Project Manager, Crew) to Discord roles in the server, so crew automatically get the right Discord role when linked
- **Enrollment settings** — magic link expiry duration, whether enrollment is open or invite-only
- **Linked accounts table** — list of all Discord-linked GearFlow profiles with the ability to manually unlink from the UI
- **Bot activity log** — last 50 bot actions pulled from the audit log, viewable in-app without needing to go to Discord

Store all config in the GearFlow PostgreSQL DB in a `discordConfig` table. The bot reads from there on startup and polls for changes every few minutes. The GearFlow admin panel reads and writes to this table directly.

---

## Tech Requirements

- Bot built with **discord.js v14** (slash commands, guild member management, channel permission overwrites)
- Hosted as a standalone Node.js service — it can live in a `/apps/discord-bot` directory in the monorepo or as a separate repo
- Communicates with GearFlow via an internal REST API or webhook endpoint (add these to the GearFlow Next.js app as needed)
- Stores minimal state itself — source of truth is always the GearFlow PostgreSQL DB
- Extend the Prisma schema to add:
  - `discordUserId` on the User/contact model
  - `discordChannelId` on the Project model
  - `discordConfig` table for bot configuration
- Use environment variables for: `DISCORD_BOT_TOKEN`, `DISCORD_GUILD_ID`, `GEARFLOW_INTERNAL_API_KEY`, `GEARFLOW_API_URL` — all other config (channel IDs, category IDs, role mappings) should live in the DB and be managed via the admin panel

---

## Architecture Notes

- Keep the bot stateless where possible — it should be able to restart cleanly and reconcile state by querying GearFlow
- Design with extensibility in mind — future phases will include more slash-command-driven forms that create and update records in GearFlow, so the command registration pattern needs to be clean and scalable
- The bot should expose a small internal API for the GearFlow admin panel to query bot status and available Discord channels/categories/roles for the config UI

### CRITICAL findings (both voices agree)
1. **Event emission = transactional outbox, polled.** No dispatcher exists. Reject: inline HTTP (fires on rollback / blocks the action), LISTEN/NOTIFY (not durable — downtime loses events), poll-ActivityLog (`logActivity` is best-effort `Promise<void>`, human-audit-shaped, no delivery state). **Build `DiscordOutbox`** (org-scoped, monotonic `id`, `eventType`, `payload`, `dedupeKey @unique`, status/attempt/nextAttemptAt), written **inside the same `$transaction`** as the mutation → rolls back with it. Bot pulls `GET /api/discord/outbox?since=cursor`, claims rows with DB lock, marks processed only after Discord succeeds. This makes `/reconcile` a *drift backstop*, not the primary recovery (the plan over-relied on it because it assumed lossy delivery).
2. **Trust boundary: per-org HMAC + global service token.** No API-key system exists. `DiscordIntegration.signingSecret` (copy WooCommerce HMAC) signs every mutation, scoped to one org (timestamp window + nonce replay cache + timing-safe compare). A global `DISCORD_BOT_TOKEN` Bearer (like existing `CRON_SECRET`) gates the outbox pull. Bot holds **zero DB credentials**.
3. **`requirePermission()` cannot be called from a session-less bot route — RUNTIME KILLER.** Existing `"use server"` actions throw on `getOrgContext()`/session lookup when there's no Better Auth session. **Fix:** extract core logic into `src/lib/services/*` `Core(orgId, actor, tx)` fns called by BOTH the server action and the discord route; the route builds a synthetic actor from the linked person and checks permission explicitly. Load-bearing refactor — naive reuse fails at runtime.
4. **`/link` security (mandatory hardening):**
   - **Enumeration oracle** → constant ephemeral response ("If that email is on file, a link was sent"), never branch on existence.
   - **Email bomb** → rate-limit per Discord user (3/hr) AND per target email (3/day), server-side.
   - **Cross-org/nullable email** → resolve `CrewMember.findFirst({ organizationId, email })` within the guild's org ONLY; 0 or >1 match ⇒ send nothing. Never global lookup.
   - **Token = victim-hijack vector — RUNTIME-CRITICAL.** Bind the **invoker's Discord ID into the token at issue time** (store in `DiscordLinkToken` row). Else attacker triggers `/link victim@email`, clicks the link, attaches their own Discord acct to the victim. The plan omits this.
   - **Token storage:** opaque `randomBytes(32)` (not JWT — need server-side single-use revocation), store **hash only**, single-use + 15-min, consume atomically (`where tokenHash AND consumedAt null AND expiresAt > now`). Reject re-link without `/unlink`.
   - Store the link on a dedicated `DiscordAccountLink`/`DiscordLinkToken` table, not `discordUserId` smeared on every people record.

### HIGH findings (both voices)
5. **Channel sync correctness:** `discordChannelId` guard prevents double-create (Discord create is not idempotent); per-project mutex serializes events; discord.js rate-limit queue + bounded concurrency for `/reconcile`; define archive policy for terminal statuses (COMPLETED/INVOICED/CANCELLED/RETURNED → lock+move, not delete); **unlinked crew = no-op + visible "pending access" warning, don't fail the sync**; **re-drive access at link time** (link-confirmed event grants all current active assignments — else assign-then-link never grants access); exclude `isTemplate:true`.
6. **`/asset fault` — RUNTIME KILLER + enum mismatch:**
   - "out of service" is **not a severity** — split into `severity = MINOR|MAJOR` + `holdForRepair: boolean`. No `OUT_OF_SERVICE` status exists → map hold → **`IN_MAINTENANCE`** (recoverable; not RETIRED/LOST).
   - **`DamageEvent.createdById` is a required `User` FK** — freelancer CrewMembers without a User will **violate the FK / 500**. Decide explicitly: (a) gate `/asset fault` on a linked User, (b) system service-User as creator + `reportedByCrewMemberId` column, or (c) make column nullable. Don't stuff into notes.
   - Status flip in the same txn as the DamageEvent, conditional on current status (don't clobber `CHECKED_OUT`); route through shared warehouse service so invariants run once.

### HIGH findings (both voices) — lock these BEFORE writing any command
1. **`BotCommand` interface (one source of truth).** Each `/commands/*.ts` exports `{ data: SlashCommandBuilder, requiredPermission, defaultEphemeral, execute(ctx), modal?(ctx) }`. `CommandContext` carries the interaction + the **resolved linked actor** (Discord ID → org + CrewMember, looked up once by the runner) + a typed `apiClient`. Runner enforces ephemeral default, catches `BotError`→renders, routes modal submits by `customId` to the **same file**. Auto-register by glob; **fail-fast on malformed/duplicate at boot** (silent skip = prod gap). TTHW target: new read command = 1 file, ~15 min.
2. **Guild-scoped command deploy, explicit script** (`npm run deploy-commands -- --guild <id>`), NOT silent-on-boot. Global commands take up to 1 hr to propagate (brutal dev loop) + re-PUT-on-boot is a rate-limit/audit hazard. Diff desired-vs-registered, PUT on change only. (Repo uses **npm**, not pnpm.)
3. **Doc-type registry derives from the existing `DocumentType` union** (`generate-pdf.ts`) — `packing-list`+`call-sheet` already exist. Bot must NOT define its own doc enum (drift). Adding a type = one registry entry, only if `generatePdf` supports it.
4. **API error envelope (machine-readable) — fix up front, retrofitting is breaking.** Existing routes return codeless `{error:"string"}`. Every `discord/*` route returns `{ ok:false, error:{ code, message, retryable, userAction?, details? }, meta:{ requestId, apiVersion } }`. Closed `code` enum (`NOT_LINKED, FORBIDDEN, ORG_NOT_CONFIGURED, ASSET_NOT_FOUND, ASSET_OUT_OF_SERVICE, VALIDATION, RATE_LIMITED, CONFLICT, IDEMPOTENCY_CONFLICT, SIGNATURE_INVALID, INTERNAL`) declared once in a **plain** `src/lib/discord/api-errors.ts` (NOT a `"use server"` file — re-exporting types from server modules crashes SSR per CLAUDE.md); bot imports the same union and switches with a `never` default so a new code can't ship without copy.
5. **`Idempotency-Key` on mutations** (`/asset/:code/fault`, `/link`) = the Discord interaction ID. Bot retries on network blips; without it, one fault click → two `DamageEvent`s. (Outbox covers inbound idempotency; command→API direction has none in the plan.)
6. **`/v1/` path prefix** — bot + app deploy independently; a breaking endpoint change silently breaks a not-yet-redeployed bot.
7. **Operator setup doc (~15 steps, plan has ~3).** Must specify: gateway intents incl. **Guild Members (privileged — toggle ON or member events never arrive)**, OAuth scopes (`bot`+`applications.commands`), bot permission bits (**Manage Channels, Manage Roles**, View Channels, Send Messages, Attach Files, Embed Links — invite URL template with bits pre-filled), the per-org HMAC secret (plan's env list omits it), and a `npm run doctor` green/red checklist (token/intents/guild/API reachability).
8. **Local-dev / testability** — biggest under-spec. Dev guild (instant deploy), injectable `apiClient`, `makeMockContext()` so `execute` is unit-tested with **zero Discord + zero network**, contract-test fixtures over **every error code** (keeps the two services in sync), `outbox:poll-once`/dry-run mode.

### MEDIUM
9. **Discord error copy = problem+cause+fix**, including DM-blocked fallback: catch discord.js `50007`, fall back to ephemeral in-channel reply with the file ("couldn't DM you, here it is privately").
