# CEO Plan: Warehouse Check Item System + Prep/Return Upgrade

Generated by /plan-ceo-review on 2026-03-23
Branch: claude/blissful-kilby | Mode: SCOPE EXPANSION
Repo: TwoToned/gearflow

## Vision

### 10x Check
A complete asset lifecycle quality system:
- Check items with photo evidence on fail
- Check history timeline on asset detail pages
- Model-level failure analytics ("SM58s fail cable check 23% of the time")
- Predictive maintenance triggers (2 failures in 3 deployments → auto-create maintenance)
- Measurement and dropdown check types beyond pass/fail
- QR-triggered ad-hoc check forms for standalone warehouse testing

### Platonic Ideal
The warehouse op forgets they're filling in a form. Scan → check form appears with exactly the right items → thumb through pass/pass/pass/pack in 3 seconds. If something's wrong, one tap flags and moves on. The PM gets a notification before the op picks up the next item. Check history is invisible until needed — then a clean timeline shows 47 passed checks, one cable failure in March, T&T retested in June.

## Architectural Decisions

### Approach B: Upgrade Existing Warehouse
The spec designed prep/return checklists as separate pages. We chose to upgrade the existing warehouse tabs instead — adding check forms as intermediate steps within the current deploy/return flow. Single surface, leverages existing scan/deploy/return code.

### Status Model: New Enums on ProjectLineItem
New `PrepStatus` and `ReturnStatus` nullable enums on ProjectLineItem. Existing `LineItemStatus` unchanged.

### Unified CheckRecord Table
Single `CheckRecord` table with `context` enum (PREP/RETURN/AD_HOC) instead of separate PrepCheckRecord/ReturnCheckRecord tables. Supports all check contexts and simplifies analytics queries.

### Reuse Existing requiresTestAndTag
No new `requiresTT` field — the existing `Model.requiresTestAndTag` drives T&T section visibility on check forms.

### Kit Checks: Kit-Level Only
When scanning a kit, show one check form for the kit's model (if configured). Don't check individual children — kits already have a verification flow.

## Schema Overview

```prisma
enum CheckItemType { PASS_FAIL, NOTES, MEASUREMENT, DROPDOWN }
enum CheckContext { PREP, RETURN, AD_HOC }
enum CheckResult { PASS, FAIL, NOTES_ONLY }
enum PrepStatus { PENDING, PULLED, FLAGGED_FAULTY, FLAGGED_TT_OVERDUE, PACKED }
enum ReturnStatus { PENDING, UNPACKED, STORED, DAMAGED, LOST }

model CheckItem {
  id               String        @id @default(cuid())
  organizationId   String
  label            String
  description      String?
  type             CheckItemType
  category         String?
  measurementUnit  String?       // for MEASUREMENT type
  measurementMin   Float?        // pass threshold
  measurementMax   Float?        // pass threshold
  dropdownOptions  Json?         // for DROPDOWN type: string[]
  createdBy        String
  createdAt        DateTime
  updatedAt        DateTime
}

model ModelCheckItem {
  id             String @id @default(cuid())
  organizationId String
  modelId        String
  checkItemId    String
  sortOrder      Int
}

model CheckRecord {
  id                      String       @id @default(cuid())
  organizationId          String
  context                 CheckContext
  lineItemId              String?      // null for AD_HOC
  assetId                 String       // always set
  bulkAssetId             String?      // for bulk asset checks
  checkItemId             String
  checkItemLabelSnapshot  String
  checkItemTypeSnapshot   CheckItemType
  result                  CheckResult
  value                   String?      // measurement reading or dropdown selection
  notes                   String?
  photos                  String[]     // S3 keys
  performedBy             String
  performedAt             DateTime
}

model WarehouseClose {
  id            String   @id @default(cuid())
  organizationId String
  projectId     String
  closedBy      String
  closedAt      DateTime
  storedCount   Int
  damagedCount  Int
  lostCount     Int
}
```
